GSD Workflow Guide

Spec-driven development workflow used to build this thesis tools site. Each tool on this site was built using the discuss → plan → execute loop below — locking decisions before planning, planning before building, to keep AI context lean and work reviewable at every step.

Click any command node to see what it does and the exact slash command to type.

Spec-driven development means locking decisions before writing plans, and locking plans before writing code. The core insight is that when implementation preferences aren’t documented upfront, AI agents make conflicting assumptions downstream — inconsistent patterns, differing architectural choices, rework. GSD forces these conversations first.

Each phase starts with /gsd:discuss-phase, which captures decisions in a CONTEXT.md file — tech choices, file locations, error handling, layout direction — as numbered entries (D-01, D-02…). These decisions are binding: the planner won’t approve plans that contradict them, and the verifier flags code that misses them.

Plans are then small enough to execute in a fresh 200k-token context, committed atomically. The result is work that is reviewable at every step — not one giant diff at the end.

Each plan runs in an isolated context with its own fresh token budget. Every task commits atomically. Work is reviewable at every step — not one giant diff at the end.

New project from scratch

Run /gsd:new-project first. It asks structured questions about your idea, spawns parallel research agents, extracts requirements, and produces an approval-gated roadmap — no code is written until you approve.

/gsd:new-project
# or, if you already have a PRD:
/gsd:new-project --auto @prd.md

--auto @doc.md — Skip interactive questions; extract requirements from a provided document or PRD.

This creates .planning/ with PROJECT.md (vision), REQUIREMENTS.md (scoped req IDs), and ROADMAP.md (phase breakdown). Then run the phase loop for each phase:

/gsd:discuss-phase 1     # lock implementation decisions → CONTEXT.md
/gsd:plan-phase 1        # research + atomic plans + verify → PLAN.md files
/gsd:execute-phase 1     # parallel waves, atomic commits

Adding GSD to an existing project

Map the codebase first so GSD understands what already exists. Without this, new-project questions will overlap with decisions already made in code.

/gsd:map-codebase        # full analysis: stack, architecture, conventions
# or faster:
/gsd:map-codebase --fast # quick tech + architecture scan only

Then run /gsd:new-project as normal — but now the questions focus on what you’re adding, not what already exists. Alternatively, if you have existing ADRs or specs, ingest them directly:

/gsd:new-project
# or ingest existing docs into .planning/:
/gsd:ingest-docs

After setup, the phase loop is identical to a new project: discuss → plan → execute per feature.

Use /gsd:progress at any point to see where you are and what command to run next.

/gsd:spec-phase N optional ▸

Clarify WHAT the phase delivers before HOW

Scores ambiguity, forces scope decisions, and produces SPEC.md before discussion begins. Use when requirements are unclear or scope is contested.

/gsd:discuss-phase N ▸

Lock in implementation decisions before planning

Asks open-ended questions about how to build the phase. Surfaces design details — layouts, API structures, error handling — to eliminate ambiguity before planning begins. Produces CONTEXT.md.

Flags

--auto — Skip interactive questions; auto-extract decisions from context.

--analyze — Analyze codebase assumptions before the discussion starts.

--power — Deep-dive extended discussion with more probing questions.

--chain — Auto-advance into plan-phase after discussion completes.

--batch — Process multiple discussion topics in a single pass.

/gsd:plan-phase N ▸

Research ecosystem, generate atomic task plans, verify

Spawns research agents, generates small task plans each executable in a fresh context, and verifies each plan achieves the phase goal. Produces PLAN.md files.

Flags

--skip-research — Skip the research agent step; go straight to planning.

--research — Force re-run research even if RESEARCH.md already exists.

--gaps — Plan only for gap tasks flagged by verify-work.

--prd <filepath> — Use a PRD file as context, skipping the discussion step.

--force — Force replan even if the phase is already marked Complete.

/gsd:execute-phase N ▸

Run plans in parallel waves with atomic commits

Runs task plans in dependency-ordered waves, each in a 200k-token context. Commits atomically per task. Keeps the main context at 30–40% capacity.

Flags

--wave N — Execute only a specific wave number.

--gaps-only — Execute only gap tasks flagged by verify-work.

--cross-ai — Force all plans through cross-AI execution.

--no-cross-ai — Disable cross-AI execution for this run.

/gsd:verify-work N optional ▸

Walk through testable deliverables, diagnose failures

Manual acceptance testing of completed work. Failures trigger diagnostic fix planning rather than manual debugging.

/gsd:code-review N optional ▸

Structured review of phase-changed files

Flags critical, warning, and info findings scoped to the phase diff.

Flags

--fix — Auto-apply fixes after review completes.

--all — Apply all findings, not only critical ones.

--files=f1,f2 — Review specific files instead of the phase diff.

--depth=quick|deep — Control review depth (quick scan vs. cross-file analysis).

/gsd:ship N optional ▸

Create PR with auto-generated body

Converts verified phase work into a pull request with summary, changes, requirements addressed, and verification status.

Flags

--draft — Create as a draft PR.

Utility Commands

/gsd:progress ▸

See current status and what step comes next

Auto-detects the next recommended command. Central hub for situational awareness between phases.

Flags

--next — Immediately run the recommended next command.

/gsd:quick [task] ▸

Execute a focused task without full phase ceremony

For small, well-scoped changes that don’t warrant a full discuss→plan→execute cycle.

Flags

--discuss — Add a lightweight discussion phase before planning.

--research — Spawn a research agent before planning.

--validate — Enable plan-checking and post-execution verification.

--full — Enable the complete quality pipeline (discuss + research + validate).

/gsd:fast ▸

Inline trivial task — no subagents, no overhead

Fastest path for truly trivial, one-step changes. No planning or subagent cost.

/gsd:debug [description] ▸

Diagnose and fix a specific problem

Runs multi-cycle debugging with persistent state across context resets.

Flags

--diagnose — Analysis only; no fixes applied.

/gsd:explore [idea] ▸

Think through an idea before committing to a plan

Socratic ideation and idea routing — explores a rough idea through guided questions, then routes it to the right next step (a phase, a capture, or a spike). Use before there’s enough clarity to discuss or plan.

/gsd:capture [topic] ▸

Capture ideas into notes, todos, seeds, or new phases

Routes ideas to the right destination without interrupting current work.

Flags

--backlog — Park idea outside the active sequence.
