Comms Layers & The Driver Insight

What separates the four directions above, and why the matrix below is laid out the way it is: the three communication layers each direction answers differently, why the stepper driver — not the brain MCU — is what actually buys concurrency, and the concurrency axis that sets complexity and the power budget, while its effect on cost depends on how the steps are generated. Expand a section to read it.

The Three Comms Layers A = brain↔screen · B = brain↔modules · C = controller↔drivers

The module schema in Part 1 is fixed — every device above carries the same six modules. What actually differs between the four directions is how three communication links are implemented, and every row in the matrix below is just one set of answers to them.

Layer A — brain ↔ screen. The touchscreen is an owned component: an ILI9341 3.2" resistive-touch TFT (bitbyg, 174 DKK ≈ €23), inspected and confirmed SPI on 2026-07-15 — 8 pins, settled, and no longer a control on this page. (Had it been the 8-bit parallel wiring the vendor listing also hinted at, Layer A would have cost ~13 pins instead of 8, which is enough to push the tightest brains over their GPIO budget — the reason the question was worth resolving rather than assuming.) Because it must render a GUI, the brain is ESP32-class in every variant — a Nano cannot hold a screen and the system logic at once. This link is where the gallery's first split lives: Console and Panel + Node wire a discrete screen to a bare ESP32 and pay Layer A in pins and wiring, while All-in-One buys an integrated screen+brain board and Layer A disappears entirely — no wiring, no pin cost, at the price of a board that is not stocked at the default vendor.

Layer B — the system bus. How the brain talks to the other modules is the first genuinely open choice: I²C, RS-485, or CAN. I²C only makes sense for a few nodes sharing one small enclosure — which is exactly the All-in-One and Console case. RS-485 is the recommended default the moment the device stops being one box: differential, ignores motor EMI, ~€0.70/node, and unchanged in cost from 2 nodes to 8 — which is why it suits Distributed Modules, where six per-pump boards each become a node. CAN earns its extra cost only with many nodes plus a real need for fault tolerance. The Bus (B) column shows this choice against the variant's real node count.

Layer C — pump-controller ↔ drivers. How the controller talks to the six stepper drivers is set entirely by the driver family: bare STEP/DIR wires for a dumb driver, a shared UART for a smart driver, or an SPI daisy-chain for a motion controller. This is the layer that decides whether a separate pump node needs to exist at all — the subject of the next section, and the reason Panel + Node is a distinct direction rather than a variation on Console.

One assumption inside Layer C is worth making explicit, because it silently sets the pin budget: the dumb-driver pin counts (S1 = 2 shared STEP/DIR + 6×ENABLE = 8) assume microstepping is jumpered — M0/M1/M2 tied to a fixed resolution, costing zero MCU pins. That is the realistic build for a pump that runs one resolution, so it is the default of the Microstepping control in Controls. Switching it to dynamic (runtime-selectable resolution) adds a shared 3-line M0/M1/M2 bus to the brain-wired dumb variants — which makes the tightest ones worse, not better. The real driver of the S1/D2 overrun is not microstepping at all; it is fanning ENABLE (or STEP/DIR) out to six physical drivers on one brain — exactly what a smart driver or a dedicated pump node removes.

The Driver Matters More Than the MCU Why Panel + Node exists only to serve dumb drivers

The instinctive question is "do I need a bigger MCU to run six pumps at once?" — but a stepper needs a driver chip regardless, and the driver you pick decides who actually generates the step pulses, which is the real cost of concurrency:

Dumb driver (DRV8825): the MCU must toggle the STEP pin for every single step, for every motor, in sync. Producing six independent, accelerating step trains is the MCU's burden — this is the only reason a plain ESP32 stops being enough and the design reaches for an RP2040 (PIO) or STM32 (hardware timers) as a dedicated pump node. That node is the Panel + Node direction: a second board whose entire job is to generate pulses the brain cannot. Push the same logic one board per pump and you get Distributed Modules.

Smart driver (TMC2209, UART velocity mode): you send the driver a target speed once, and the driver generates its own steps. The MCU is nearly idle, so it stays fused — one ESP32 doing brain and pump-control together — even at six-parallel. This is what makes Console and All-in-One viable at full concurrency: the T9-fused-i2c and T9-fused-485 rows run all six pumps with no separate pump-node MCU at all. TMC2209 is also silent, runs cooler, and supports sensorless homing — practical bonuses that come free with the same chip.

Since a driver is bought either way, the smart driver's advantage is structural: it buys full parallel capability outright and keeps the MCU fused, with no co-processor — which makes the "which MCU" question almost irrelevant. Whether it is also the cheaper route depends on the driver's price at the chosen vendor; on this project's primary vendor no Trinamic driver is stocked, so the dumb-driver builds are the ones actually sourced (see the recommendation in Part 5). The durable insight the matrix makes visible is that driver family, not brain choice, is what actually buys (or avoids) concurrency.

Read the gallery through that lens and it collapses into one question. Panel + Node and Distributed Modules spend boards, wiring and enclosure complexity to buy step-generation the brain cannot supply — a bill that a smart driver simply deletes. They earn their keep on other grounds (hot-swap servicing, per-pump isolation, physical layout), not on concurrency. If concurrency is all you want, the fused directions win.

The Concurrency Axis Sets complexity and the power budget; its effect on cost depends on the driver

Reading the matrix by concurrency shows one axis dominates the physical design: how many pumps must move at the exact same instant. Rows at 1–2 concurrent (S1*, D2*) sit at ★–★★ complexity on a 60 W PSU. Committing to true 6-parallel moves every row to a 150 W PSU and at least ★★☆☆ complexity, regardless of which driver or bus is chosen — concurrency, not driver family, sets the floor complexity and the power budget.

Cost, by contrast, is not fixed by concurrency alone — it is set by how the extra step-generation is provided. Because a smart driver can deliver six-parallel with no co-processor at all, whether full concurrency is cheap or expensive depends chiefly on driver family and on what each part actually costs at the chosen vendor (the prices on this page are editable for exactly that reason). The rows that buy concurrency with a dedicated pump-node MCU sit at the expensive end regardless.

That is because parallelism is not just a firmware problem: six motors moving at once draw roughly six times the peak current of one, which means a larger PSU, more heat, thicker wiring, and more EMI — a real penalty for a portable point-of-care device, on top of whatever the step-generation solution costs.

This question — does the dispensing protocol actually need liquids moved independently or simultaneously — is examined in the companion multi-liquid architecture study ↗, which owns the decision between a shared-step-bus serial layout and independent per-motor parallel control. This tool prices what each answer costs; it does not settle the choice itself.

Is it just a count? No — there is a second, deeper limit. The question you should worry about is not only "are there enough pins?" but "can each function actually reach a pin without two things fighting over it?" On the ESP32 the answer splits cleanly:

What the count already covers. The ESP32 routes almost every digital function (SPI, I²C, UART, PWM) through an internal GPIO matrix — unlike an Arduino, a peripheral is not nailed to a fixed pin, so any free output-capable GPIO will do. That is exactly why a raw count is a fair first-order test: if the pins exist, the routing almost always follows. The only pins that break this are the four input-only ones (GPIO 34/35/36/39 — no output, no pull-up: fine for a touch-IRQ or a FAULT line, useless for STEP/DIR/CS), the flash pins (6–11, gone), and the strapping pins (0/2/5/12/15, usable with boot caveats). The digital-vs-analog split barely matters here: every sensor is digital I²C, so the one analog gotcha — ADC2 going dead whenever Wi-Fi is on — only applies if you later add an analog probe, and even then ADC1 (GPIO 32–39) stays free.

What the count does not cover — the real "TX for two things" trap, now checked per row. A pin count cannot see that the ESP32 has only 3 UARTs, 2 I²C, 2 usable SPI controllers. Six TMC2209s can't share one UART line (their address field is 2 bits = 4 drivers max), so six need two UART lines; add an RS-485 system bus and the programming/debug console and you are asking for four UARTs from a chip that has three. The matrix now runs this second check on every variant: expand any row to see its Peripheral controllers line (UART/I²C/SPI demand vs 3/2/2), and a ⚠ UART 3/3 flag rides the pin column when a build spends every UART. Only T9-fused-485 lights it up — it passes nothing to spare — while T9-fused-i2c stays clean: an I²C system bus spends no UART, leaving both spare UARTs for the two TMC lines. Resolvable (bit-bang one TMC line on SoftwareSerial, or drop the console after flashing), but a real build-time constraint the count alone would miss.

A note on ENABLE — the fan-out is deliberate, not waste. The six ENABLE lines that make the dumb-driver rows overrun are a feature for a battery device: switching each DRV8825's ENABLE in software gates that motor's current draw, so idle pumps draw nothing. Worth knowing that a smart driver gives the same per-motor power control over the shared UART — TMC2209 disables a driver and sets its run/hold current (IRUN/IHOLD, TOFF) by register, no GPIO spent — so the fused-TMC path keeps the battery benefit without the six-pin cost. The full per-component signal map, both ceilings, and every overrun variant worked pin-by-pin live in PIN-BUDGET-ANALYSIS.md ↗ — the permanent cross-check reference for this section.

Part 5

Architecture Decision & Recommendation

A synthesis of the two companion tools — this Explorer (cost and pin budget) and the Dispense Throughput Simulator ↗ (run time) — into a single defensible recommendation. Every candidate architecture in the matrix above was weighed on its own trade-offs; the reasoning below proceeds through three ordered filters — feasibility, then cost, then run time — reflecting the design priority that a portable point-of-care instrument must first be buildable, then affordable, and only then fast. Concurrency is examined first, because it frames everything after it: if full parallelisation could be had for essentially the same price and complexity, the extra capability would be free and the choice obvious — so it is worth establishing up front how much parallelism is actually worth paying for.

Decision framework & fixed premises

Three premises are treated as settled for this device and constrain the search before any variant is compared:

  • The device is a portable, single sealed-enclosure point-of-care instrument, so all six modules share one small housing. I²C is therefore the appropriate system bus; RS-485 and CAN earn their additional cost only across physically separated nodes, which this device does not have, and are out of scope here.[1]
  • Selection priorities, in order: (i) feasibility — the build must be realisable and its parts sourceable; a single controller is preferred, but a small helper co-processor is acceptable where the pin budget requires one; (ii) unit cost, weighted explicitly above speed; (iii) throughput.
  • All pumps run a single shared step rate. Differing per-liquid volumes are metered by step count, not by independent pump speeds, which removes any requirement for independent-rate motor control and, with it, an entire axis of driver complexity.

Step 1 — Concurrency: how much parallelism is worth buying

The throughput simulator sweeps concurrency K (the number of pumps dispensing at once) from serial to fully parallel.[2] Under the realistic point-of-care load (PANPOC: 300/5/300/50 µL, 32 samples) the saving relative to serial operation shows strong diminishing returns:

PANPOC load, 32 samples, fixed clock — total run time and saving vs. serial (K=1).

K = 1 (serial)399.3 s—
K = 2245.2 s−38.6 %
K = 6 (full)220.8 s−44.7 %

K = 2 captures ~86 % of the maximum attainable saving. The residual is bounded by a single high-volume station whose dose time floors the per-sample cycle, so concurrency beyond K ≈ 2 buys little time the bottleneck will permit. This does not, on its own, rule out full parallelism — if six-at-once turns out to be equally cheap and feasible, the extra headroom is worth taking; Step 1 only establishes that time alone does not justify paying much for it, leaving that verdict to the cost and feasibility steps. On time economics alone, then, K = 2 would be the sensible ceiling — and that is where this analysis first landed. Step 3 overturns it: once the pumps are allowed to share a single step clock, full six-at-once costs only about €3 more on a ~€235 device — comfortably inside "take the free headroom." Whether the protocol genuinely requires simultaneous rather than serial dispensing is examined in the companion multi-liquid architecture study.[4]

Step 2 — Feasibility: can one controller do it, or is a helper needed?

The controller must drive all six pumps — one stepper driver each — while also rendering the touchscreen GUI, talking to the other modules over the system bus, and offering wireless connectivity for loading protocols and firmware. That combination points to an ESP32-class brain rather than a bare Arduino: it pairs ample GPIO and processing headroom to host a GUI with built-in Wi-Fi/Bluetooth, at a low unit cost.[5] The open question is whether that single ESP32 can also generate the step signals for all six drivers, or whether a helper is required.

The owned ILI9341 touchscreen is wired SPI and already commits 8 of the ESP32's 16 usable GPIO, plus 1 more for the SD card's chip-select (it rides the screen's SPI bus, so it costs only its own select line) — 9 of 16 spent before a single pump is connected.[1][5] Once that is spent, fanning STEP/DIR or ENABLE lines out to six discrete dumb drivers[6] overruns the pin budget — so a single-brain dumb-driver build cannot be wired as one board.[3] This is independent of concurrency: all six drivers must be individually addressable even when only two move at once, so the six-way fan-out is unavoidable regardless of K. Two routes restore feasibility: offload the six-driver fan-out to a small helper MCU (a co-processor pump-node), or use a smart driver whose single shared UART replaces the wide parallel wiring.[7] Designs that still overrun after this — the fused dumb-driver rows — are not buildable on the chosen brain and are excluded from further consideration.

A third route, which the shared-rate premise unlocks. Because every pump runs at the same rate, all six drivers can share a single STEP/DIR clock, each pump dropping out via its own ENABLE line the moment it reaches its dose. That removes the need for six independent step trains — the very thing that normally forces a co-processor onto a dumb-driver 6-parallel build — and it is generated by a hardware timer peripheral, so it keeps ticking regardless of what the CPU is doing. What is left is six ENABLE lines plus the two alignment motors, and how those are placed is what separates the three shared-clock builds:

  • SC6-rp-i2c — one small RP2040 node carries everything (six ENABLE + two alignment motors), replacing the two Arduino Nanos with a single cheaper board.
  • SC6-exp-i2c — no helper MCU at all: a €6.53 MCP23017 I²C expander carries the ENABLE and alignment lines. Cheapest, but it puts the dose-critical ENABLE lines behind the I²C bus and fills the expander to 16/16.
  • SC6-s3exp-i2c — an ESP32-S3-Nano brain, whose larger pin count keeps the six ENABLE lines on direct GPIO while only the slow alignment/homing ride the expander. One MCU, dose-critical signals deterministic, and the faster core the GUI wants.

All three absorb the two alignment motors, removing the separate alignment node entirely.

On the prices. This tool costs each build against the components actually stocked by the project's primary vendor (bitbyg.dk) — a Danish reseller chosen for fast shipping, at the price of higher unit costs than direct import. The same tool is reusable for any other sourcing: entering figures from cheaper direct (e.g. Chinese) suppliers simply re-ranks the identical builds. Absolute costs will therefore shift with the vendor and with market fluctuation, and would be revisited for a production run — but the structure the tool imposes (feasibility, concurrency, driver family, cost) is vendor-independent. Having guided this prototype's architecture, it stands as a general instrument, proven on this specific case, for re-costing the design under different suppliers or future price changes.

Motion profile, priming & calibration

Velocity profile. Dispensed volume equals step count × µL/step and is independent of pump speed; an acceleration ramp exists solely to guarantee that no steps are lost near the motor's start/stop (pull-in) rate.[8][10] Because all pumps share one clock and identical hardware, a single trapezoidal ramp covers every active pump at once — accelerate together, cruise, each pump disables at its own target step count, then decelerate. A brute stop is acceptable: peristaltic occlusion is self-braking and the stepper's holding torque resists coasting, so the ramp matters chiefly on start.

Priming and calibration. Both run one pump at a time — the simplest case for every candidate, being a single-pump subset of the concurrent schedule. They rely only on per-motor ENABLE addressing, the same mechanism that lets a pump drop out of a concurrent group when it reaches its dose. Calibration derives each pump's true µL/step and is applied as a per-pump step-count correction — never a speed change — which keeps it consistent with the shared-rate premise.

Recommendation — the final design

SC6-s3exp-i2c — a single ESP32-S3-Nano brain, no co-processor, running all six pumps from one shared STEP/DIR clock with per-pump ENABLE on direct GPIO, and a single MCP23017 I²C expander carrying only the alignment motors and homing switches (€103.34 controller / €248.30 whole-system, all six dispensing at once).

Two premises make this the answer rather than a compromise. First, because the pumps share one rate, a single hardware-timer clock drives all six — so full six-at-once parallelism is essentially free: the shared-clock RP2040 build (SC6-rp-i2c) costs only ~€3 more than the K=2 Nano baseline while improving point-of-care run time from −38.6 % to −44.7 % vs serial. With parallelism no longer a cost question, the design goal becomes the fewest processors and the smoothest interface.

Second, one MCU beats two. A second processor is not just a chip — it is a second firmware, a second toolchain, and an inter-processor command protocol to design, implement and debug (framing, timeouts, retries, aborts). For a one-person thesis that is the single largest firmware cost, and collapsing to one MCU deletes it outright. The classic ESP32 cannot fuse the whole system — the six ENABLE lines would have to go behind the I²C expander — but the ESP32-S3-Nano's larger pin count is exactly what removes that compromise: the six dose-critical ENABLE lines stay on direct GPIO (single-instruction, deterministic, and able to disable the pumps even if the I²C bus hangs — a fault-tolerance property the expander-only build cannot offer), while only the slow, jitter-tolerant loads — the two alignment motors, the homing switches, and any future dynamic microstepping — ride the MCP23017. The brain sits at 20 / 21 pins (3 spare if the screen is wired to 6 pins), the expander at 10 / 16 (6 spare). As a bonus, the S3's faster LX7 core and octal PSRAM are the best brain here for the smooth GUI the instrument is meant to have.

Why not the two cheaper shared-clock builds. SC6-exp-i2c (fused ESP32 + expander, €237.42) is €10.88 cheaper but forces the dose-critical ENABLE lines onto the I²C expander and fills it to 16 / 16 with no headroom. SC6-rp-i2c (ESP32 + RP2040 node, €238.26) is a clean, sourceable two-MCU build — but it is two MCUs, which is the very cost the S3 was chosen to avoid. The S3 design's ~€10 premium buys a single firmware, the dose-critical signals on real GPIO, and the UI headroom — the best-value trade for this project.

Recommendation — the build for prototyping

DOIT ESP32 (30-pin) + the two Arduino Nanos already in-house, running the same shared-clock firmware — a bench rig to validate the design before committing to the S3.

The final design carries exactly one unproven behaviour: does a DRV8825 stop precisely on its step count when ENABLE is dropped mid-clock? That is a per-pump property, so it does not need the full build to test. The prototype needs only a brain (the DOIT ESP32 at €9.05, which the project must buy regardless), the Nanos already owned, and — to start — two DRV8825s and the 72 W supply: run both on one shared clock, drop one ENABLE early, and confirm its dosed volume matches its step count while the other keeps running. Scale to six only once it holds. Migrating to the final design is then a board swap (two Nanos → one S3-Nano) and a firmware port; the control scheme is identical, so what the prototype proves carries straight over.

The open item, either way, is that ENABLE-gating dose-accuracy check — the one experiment that de-risks the whole shared-clock family. A secondary item is confirming the ESP32-S3-Nano's pinout against the manufacturer diagram, since the final design sits one pin from its usable ceiling and the 21-pin figure is vendor-stated rather than datasheet-audited.
