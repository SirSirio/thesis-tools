# Phase 6.1: Architecture Refinement - Context

**Gathered:** 2026-07-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Refine `tools/system-architecture-explorer/` from a pump-control cost matrix into a
**whole-device architecture page**:

1. **Part 00 — module schema.** A new intro section at the very top: what the system is,
   which six modules it has (pump, alignment, nozzle, storage, UI, software/electronics),
   what hardware each carries, and how liquid and data flow between them.
2. **Design-direction gallery.** 3–4 curated, visually presented device concepts
   (screen-integration × control-topology combinations), each an SVG sketch + a few words.
3. **Design-type matrix column.** Every variant tagged with its direction; sortable,
   filterable, shared filter state with the gallery.
4. **New components in the model.** Nozzle vibration motor, capacitive touch-sensing module,
   and 2× 28BYJ-48 priced into the cost model; power-rail questions researched and reflected.
5. **Consistency pass.** Fix the known drift between the tool, its SPEC.md, and the three
   decision records in `prototypes/System-Architecture/`.

**Not in scope:** making the architecture decision itself; landing-page work; any new tool.

</domain>

<decisions>
## Implementation Decisions

### Part 00 — module schema
- **D-01:** Schema sits **at the very top** of the page, preceded by a **very short intro**
  (a short paragraph or less) about what the page contains.
- **D-02:** **The current page introduction is obsolete and must be rewritten entirely** to
  reflect the new page (schema → directions → matrix funnel). Do not patch it — replace it.
- **D-03:** Schema is **interactive: hover/click highlights a module** and reveals its
  hardware payload / one-sentence purpose in a side note.
- **D-04:** Module boxes carry **payload chips** naming their electronics (6× NEMA17,
  2× 28BYJ-48, vibration motor, capacitive sensing ×6 containers, screen+SD+LM75). The
  schema doubles as the hardware-requirements baseline.
- **D-05:** **Both liquid flow and data flow are drawn, plus the liquid barrier** around the
  electronics. Visual language is free — creative, elegant, modern; Sirio likes a
  **liquid-glass aesthetic**. His sticky-note sketch defines connectivity only (see
  CONTEXT-SEED for the transcription); spatial layout is fully free. **Tube-holding module
  no longer exists** — the custom rack is part of the alignment module.

### Design-direction gallery
- **D-06:** A direction = a **screen-integration × control-topology combination**, curated
  into **3–4 distinct device personalities** (e.g. all-in-one integrated-screen build,
  classic brain + pump node, modular hot-swap). Leftover matrix rows get tagged with the
  nearest direction.
- **D-07:** Each direction = **stylized SVG device sketch + name + 1–2 lines**. The graphic
  carries the description ("described without many descriptions").
- **D-08:** Gallery sits **between the schema and the matrix**; **clicking a direction card
  filters/highlights its rows in the matrix** — the page reads as one funnel:
  system → possible shapes → compare on price & functionality.
- **D-09 (important, updates Phase-6 D-11 emphasis):** **Design ideation is
  vendor-independent.** Generate direction concepts first from knowledge + general web
  search; only THEN check bitbyg for available/compatible components. bitbyg remains the
  default *pricing* vendor, but idea generation must not be limited by its catalogue.

### Design-type column
- **D-10:** Column values = the **curated direction names**, rendered as **colour-coded
  chips**. Column, gallery, and filter share one vocabulary.
- **D-11:** **The matrix table may run wider than the standard content column** (Sirio
  approved a break-out container). Page-level no-horizontal-scroll still applies at the
  usual viewports.
- **D-12:** Column is **sortable and filterable** — a direction filter joins the existing
  max-price/complexity/concurrency controls and **shares state** with gallery click-to-filter
  (same state, two entry points).

### New components & power
- **D-13:** **Vibration motor and 2× 28BYJ-48 are fixed** (join the shared block, constant
  across variants). The second 28BYJ-48 **replaces the "alignment motor #2 TBD"
  placeholder** in the tool and in ARCHITECTURE.md.
- **D-14:** **The screen is charged only to variants that actually use it.** Integrated
  ESP32-screen variants (with a sufficiently large screen) must never be billed for the
  standalone ILI9341 — extend/verify the existing double-count guard for all
  screen-scenario combinations.
- **D-15:** **28BYJ-48 voltage (5 V vs 12 V) is a research question**, decided together
  with the **step-down-from-24 V rail design** ("I will need to downsize from 24 V
  anyways") — compare options at the component level (regulators/buck converters included),
  then reflect the answer in the power-rail model and BOM.
- **D-16:** **Vibration-motor drive scheme: research decides fully.** Candidates include
  transistor/MOSFET + flyback + PWM from 5 V, a dedicated ~3 V rail, series resistor, a
  driver module, or swapping to a different vibration motor type. (Physics prior recorded:
  12 V direct drive on a 3 V brushed motor is ~16× rated power — expect research to rule
  it out.) Burst-only duty is the requirement.
- **D-17:** **Temperature compensation is a future software hook**, noted on the UI module
  only — one line, no modelling, no cost impact. The note should mention **dispensed-volume
  effects (liquid thermal expansion) and viscosity**; exact wording is Claude's discretion
  (Sirio is more worried about volume expansion; physically viscosity typically dominates
  water-like liquids' behaviour change per °C — pick the physically apt phrasing).

### Consistency pass (from the seed scan — all confirmed by searches)
- **D-18:** Fix in this phase: SPEC.md's 19-vs-20 variant count; ARCHITECTURE.md's stale
  "confirm SPI vs parallel" warning (resolved 2026-07-15 — SPI, High confidence);
  SPEC.md power-model table's pre-bitbyg PSU prices (€12/€20 → €18.26/€31.66) and the
  stale "only the ILI9341 is sourced" assumption note; add a dated "prices superseded by
  the tool" preface to PUMP-CONTROL-CONCEPTS.md rather than rewriting its numbers;
  resolve the alignment-motor-#2 TBD (per D-13).

### Claude's Discretion
- Exact visual treatment of the schema (liquid-glass rendering, chip styling, flow-line
  style, enclosure/barrier representation) and of the direction sketches.
- Direction names and the final count (3 vs 4), given the curation rule in D-06.
- Which existing matrix column (if any) gets demoted/moved despite the wider container.
- Temp-compensation note wording (D-17).
- How the new fixed parts are grouped in the component table (new "module hardware"
  section vs appended to shared block rows).
- `PRICES_VERSION` bump handling when new DEFAULTS entries land (required by Phase-6 D-06).

</decisions>

<specifics>
## Specific Ideas

- "Liquid glass" — Sirio's named aesthetic for the schema's boxes/flows.
- The page should read as a **funnel**: what the system is → what shapes it could take →
  what each shape costs. The rewritten intro frames exactly that.
- Direction cards are the creative centrepiece: device-impression sketches (where the
  screen sits, one box vs several), not abstract topology charts.
- The schema payload chips are the "current requirements in terms of what the system will
  have — some basic hardware" baseline Sirio described.
- UI module: protocol is "set on a laptop and forget" via the screen's SD slot; a USB
  reader is a possible later addition (noted, not built — see Deferred).
