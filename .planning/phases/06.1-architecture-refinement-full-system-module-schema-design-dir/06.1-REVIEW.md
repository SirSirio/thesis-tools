# Phase 06.1: Code Review Report

**Reviewed:** 2026-07-16
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

The new Part 00 module schema, the design-direction gallery, and the extended `pinsOf()` are
structurally sound: `directionOf()` genuinely partitions all 20 variants 2/2/8/8 with no
unclassified bucket (verified by evaluating the shipped `VARIANTS`/`DIRECTIONS` constants),
`SHARED_BOM` sums to exactly the advertised €149.65, the component confidence census (17 High /
2 Medium / 7 Low of 26) is accurate, the D-13 `+1` PWM pin flips no variant's feasibility, the
`escapeHtml`/`textContent` discipline around `MODULES` and `sourceCellContent()` is real, and the
landing-page i18n was updated in both `en` and `it` dictionaries. The state-sync paths flagged in
the prior cycle (`PRICES_VERSION`, the `skip` argument in `syncCompRow()`, DOM seeding of
`interfaceMode`/`includeShared`, the `>=0` price clamp) are all still intact.

The defects are elsewhere, and they are numeric. **The rebuilt `SHARED_BOM` silently broke the
"whole-system cost" view outright** — every variant now prices above the €200 ceiling of the
`#fPrice` slider, so toggling the control empties the entire matrix. Separately, the canonical
`SPEC.md` states several per-variant numbers that the shipped constants do not produce, and the
tool's own Part 01 theory prose still quotes the pre-sourcing prices it was promoted to replace —
including an argument that is now *inverted* by its own price table.

## Critical Issues

### CR-01: "Whole-system cost" toggle empties the entire matrix — regression introduced by the rebuilt SHARED_BOM

**File:** `tools/system-architecture-explorer/index.html:450` (`#fPrice`), `:616` (`SHARED_BOM`), `:1403` (filter)
**Issue:** `SHARED_BOM` was rebuilt this phase from `{stepperNema:6, screen:1, nano:1, drv8825:1, align28byj:1, alignMot2:1}` (**€137.22**) to `{stepperNema:6, screen:1, nano:1, align28byj:2, vibMotor:1, vibDriver:1, capTouch:1, buck12:1, buck5:1}` (**€149.65**). The `#fPrice` slider still has `max="200" value="200"`, and `renderMatrix()` filters on `o.cost<=maxPrice`.

Evaluating the shipped constants:

| | cheapest whole-system variant |
|---|---|
| before this phase | `T9-fused-i2c` **€195.18** ≤ 200 → rows visible |
| after this phase | `ESPINT-fused-i2c` **€207.61** > 200 → **0 rows** |

All 20 whole-system costs now fall in €207.61–€341.48, i.e. **every** row exceeds the slider's maximum. Selecting "Yes — whole-system cost" therefore renders `0 of 20 variants shown.`, blanks `#diagram`, resets `diagramCaption` to the generic label, and sets `selectedVariantId=null` (`:1445`). The slider is *already at its max*, so the reader has no way to recover and no indication the ceiling is the cause — the tool simply appears to have no whole-system data. This is the tool's headline SC-5 output and the reason four of the five new components exist.

**Fix:** make the range depend on the view instead of hard-coding a controller-only ceiling:
```html
<input type="range" id="fPrice" min="20" max="400" step="1" value="400">
```
and rescale on toggle so the default stays "show everything":
```js
const PRICE_MAX = { ctrl: 200, full: 400 };
function setPriceRange(){
  const el = document.getElementById('fPrice');
  const max = PRICE_MAX[includeShared ? 'full' : 'ctrl'];
  el.max = max;
  if (+el.value > max || +el.value === +el.dataset.prevMax) el.value = max; // keep "at max" sticky
  el.dataset.prevMax = max;
  maxPrice = +el.value;
  document.getElementById('maxPriceLbl').textContent = maxPrice;
}
document.getElementById('fShared').addEventListener('change', e => {
  includeShared = e.target.value === 'full';
  setPriceRange(); renderMatrix();
});
```
Call `setPriceRange()` in the init block (after `includeShared` is seeded from the DOM, `:1504`) so a browser-restored "full" selection scales the slider too. Add a regression check to the SPEC: *min whole-system cost must remain ≤ the slider maximum whenever `DEFAULTS`/`SHARED_BOM` change* — the same class of invariant `PRICES_VERSION` already guards.

### CR-02: SPEC states `ESPINT32-brain-i2c` "fits (1 pin free)" — the shipped tool computes 0 free

**File:** `tools/system-architecture-explorer/SPEC.md:259` (vs `tools/system-architecture-explorer/index.html:738-753`)
**Issue:** SPEC's variant-BOM section says of `ESPINT32-brain-i2c`: *"It fits (1 pin free)."* Running the shipped `pinsOf()` against the shipped constants:

```
avail = COMP.espscreen32.gpioUsable = 3
used  = 0 (integrated → Layer A + LM75 skipped)
      + BUS_PINS['I²C'] = 2
      + v.pinsC = 0
      + 1  (D-13 vibration-motor PWM pin)
      = 3   →  free = 0
```

The variant reads **`0 free`** in the matrix, not `1 free`. The D-13 `+1` PWM pin added this phase consumed the last pin, and the prose was not updated — SPEC is internally inconsistent, since its own pin formula at `SPEC.md:306-321` *does* include the `+1` term. This is the single number the whole `ESPINT32-brain-i2c` narrative rests on ("its only viable shape is a pure brain… It fits"), and CLAUDE.md makes SPEC.md canonical.

**Fix:** in `SPEC.md:259` replace `It fits (1 pin free).` with:
```
It fits with **zero** pins to spare (3 avail = 2 I²C + 1 vibration PWM) — the D-13 vibration
pin consumes the last free GPIO, so this variant has no headroom for any further fixed load.
```

### CR-04: The tool's own Part 01 theory quotes pre-sourcing prices and makes an argument its price table now inverts

**File:** `tools/system-architecture-explorer/index.html:362-375, 380-383`
**Issue:** The shipped theory prose contradicts the constants 200 lines below it in the same file:

| Theory prose | Shipped `DEFAULTS` |
|---|---|
| `:362` "Dumb driver (DRV8825, **~€1.5**)" | `drv8825.eur = 6.87` |
| `:366` "Smart driver (TMC2209 … **~€3.5**)" | `tmc2209.eur = 3.5` ✓ |
| `:372` "spending roughly **€2 more per driver** on a smart part" | TMC2209 is **€3.37 cheaper** per driver than DRV8825 |
| `:380-383` "Rows at 1–2 concurrent (S1*, D2*) **sit around €29–30**" | S1/D2 compute to **€72.53–€77.55** |

The "€2 more per driver" argument is not merely stale, it is **backwards**: on the tool's own bitbyg prices, six TMC2209s cost €21.00 against €41.22 for six DRV8825s, so the smart driver is the cheaper part *and* buys concurrency. `SPEC.md:186-188` explicitly records this ("DRV8825 €1.5 → €6.87 … ~4.5× the generic estimate previously assumed") — the spec knows, the shipped page does not. A cost tool that prints "~€1.5" for a €6.87 component beside its own €6.87 table is stating a fact it disproves on the same screen, and phase 06.1's stated purpose was to make this page the canonical source. (Provenance: the prose predates this phase — but this phase rewrote the adjacent shared-block footnote and removed the ±20% caveat while leaving these untouched.)

**Fix:** in `:362`/`:366` drop the hard-coded prices and defer to the live table, and correct the conclusion in `:372`:
```html
<p><b>Dumb driver (DRV8825):</b> the MCU must toggle the STEP pin …</p>
<p><b>Smart driver (TMC2209, UART velocity mode):</b> you send the driver a target speed once …</p>
<p>Since a driver is bought either way, the smart part is the better buy twice over — on the
sourced bitbyg prices in the table below it is <i>cheaper</i> per driver than the DRV8825
(€3.50 vs €6.87) and it buys full parallel capability outright, making the "which MCU"
question almost irrelevant.</p>
```
For `:380-383`, quote the cluster ranges from the live matrix (S1/D2 ≈ €72–78 controller-only; 6-parallel €66–€192) or, better, state the *ratio* rather than absolute euros so the prose cannot drift again on the next sourcing pass.

### WR-02: MPR121/LM75 pin cost is silently skipped for every integrated board — correct only by accident

**File:** `tools/system-architecture-explorer/index.html:744-747`
**Issue:** `if (!intKey) { used += SCREEN_PINS[...]; used += (v.b === 'I²C') ? 0 : 2; }` folds the MPR121 into the LM75 term *and* gates both on "not an integrated board." The LM75 skip is justified (it ships on the owned ILI9341 module — see the vendor URL at `:592`), but the **MPR121 is storage-level sensing and has nothing to do with the screen**. `SHARED_BOM` (`:616`) includes `capTouch:1` for *every* variant including integrated ones. The code is correct today only because all three integrated variants happen to use `b:'I²C'` (where the term would be `+0` regardless). Add an integrated-screen variant on RS-485/CAN and its MPR121 attachment costs 0 pins instead of 2, with no error — exactly the silent-drift class this file's other guards are written against.
**Fix:** split the terms so each models its own hardware:
```js
if (!intKey) used += SCREEN_PINS[interfaceMode];       // Layer A
if (!intKey) used += (v.b === 'I²C') ? 0 : 2;          // LM75 — ships on the discrete ILI9341 module only
used += (v.b === 'I²C') ? 0 : 2;                        // MPR121 — storage sensing, present on EVERY variant
```
Note this *changes* the current numbers only for a hypothetical non-I²C integrated variant (none exist), so it is a safe refactor. Update `SPEC.md:306-321` and the `:729-737` comment ("skipped for espscreen, which has no LM75") to state the two reasons separately.

### WR-03: Init writes `selectedDirection` directly, bypassing the function documented as "the ONE place" it is written

**File:** `tools/system-architecture-explorer/index.html:1516-1521` (vs `:676-686`)
**Issue:** `setDirection()` carries the invariant *"the ONE place `selectedDirection` is written … Validates key against DIRECTIONS (T-06.1-08): an unrecognised key degrades to the no-filter sentinel rather than being trusted."* The init block then writes the variable directly and hand-duplicates the card `.selected`/`aria-pressed` sync loop — skipping the `DIRECTIONS[key]` validation, and leaving two copies of the same six lines to maintain. An unvalidated value reaching `selectedDirection` makes `renderMatrix()`'s filter (`:1404`) match nothing → empty matrix.

There is a second problem in the same lines: the comment claims "the same WR-04 reasoning as `interfaceMode`/`includeShared`", but `#fDir`'s options are created by `populateDirectionSelect()` at `:1511`, i.e. they **do not exist in the HTML at parse time**, so browser form-restoration cannot target them the way it can for the statically-authored `#ifMode`/`#fShared`. The seeding is inert at best; if Firefox does restore the value after this inline script runs, `selectedDirection` and the `<select>` disagree with no re-render to reconcile them.
**Fix:** delete `:1516-1521` and let the one writer do its job — it already syncs the select, the cards, and re-renders:
```js
setDirection(document.getElementById('fDir').value);   // 'any' → validated to null
```
`setDirection()` calls `renderMatrix()`, so drop the trailing `renderMatrix()` at `:1522` or leave it (idempotent). Amend the comment to say the seeding is defensive only, since dynamic options are not browser-restorable.

### WR-04: Reset clears the persisted rate but leaves the live rate — the next keystroke resurrects it

**File:** `tools/system-architecture-explorer/index.html:1484-1487`
**Issue:** Reset restores `COMP[k].eur` from `DEFAULTS` and removes `sae-prices`, `sae-prices-v`, **and `sae-rate`** — but never resets the in-memory `rate` or the `#rate` input. So after Reset with a custom rate: the DKK column still recomputes against the custom rate; and the first subsequent price edit calls `persist()` (`:1374`), which writes `sae-rate` back with the very value Reset just deleted. Reset is not idempotent, and `SPEC.md:511` claims it "restores all `DEFAULTS` and removes all three keys" — the removal is real but does not stick. Either the rate is in scope (then reset it) or it is not (then do not delete the key).
**Fix:** make the behaviour match the SPEC claim:
```js
document.getElementById('reset').addEventListener('click',()=>{
  for(const k in COMP) COMP[k].eur=DEFAULTS[k].eur;
  rate = 0.134;                                   // DEFAULT_RATE — hoist to a const, it is magic in 3 places
  document.getElementById('rate').value = rate;
  try{ localStorage.removeItem('sae-prices'); localStorage.removeItem('sae-prices-v'); localStorage.removeItem('sae-rate'); }catch(e){}
  renderComps(); updateConv(); renderMatrix();});
```
`0.134` is currently a magic literal at `:429`, `:666` and `:1473` — hoist it to `const DEFAULT_RATE = 0.134;` while fixing this.

### WR-06: Two schema data-flow lines are drawn straight through the Alignment module box

**File:** `tools/system-architecture-explorer/index.html:1059-1071`
**Issue:** With `el = {x:270, y:440, w:340}` and `anchorStep = el.w/6 ≈ 56.67`, the Electronics→**Pump** link (anchor x≈383.3 → 330,190) and the Electronics→**Nozzle** link (anchor x≈496.7 → 540,190) both traverse the full height of the Alignment box (`x 330–550, y 250–370`) — verified geometrically; the Storage and UI links clear it. ### WR-07: The €149.65 shared-block breakdown is hand-copied prose that duplicates SHARED_BOM × DEFAULTS

**File:** `tools/system-architecture-explorer/index.html:504-508`
**Issue:** Nine component prices and their total are hard-coded in the shipped markup (`Shared block ≈ €149.65 (6× NEMA17 €86.46 · ILI9341 screen €23.32 · …)`). They are correct today (verified: sums to exactly €149.65), but they are a third copy of data already in `DEFAULTS` and `SHARED_BOM` — and unlike those, nothing recomputes them. They go stale the moment a `DEFAULTS` price is edited (with no `PRICES_VERSION`-style guard), and they are *immediately* wrong for any reader who edits prices in the live table, since every other cost readout on the page updates and this one does not. The exact same hand-copy just produced CR-03 in the SPEC.
**Fix:** compute it from the constants it describes:
```js
function sharedBlockSummary(){
  const parts = Object.keys(SHARED_BOM).map(k =>
    `${SHARED_BOM[k]>1?SHARED_BOM[k]+'× ':''}${COMP[k].label} €${(COMP[k].eur*SHARED_BOM[k]).toFixed(2)}`);
  const total = Object.keys(SHARED_BOM).reduce((s,k)=>s+COMP[k].eur*SHARED_BOM[k],0);
  return `Shared block ≈ €${total.toFixed(2)} (${parts.join(' · ')}).`;
}
```
Give the `<p>` an id, write it via `textContent` in `renderComps()` (so it tracks live edits), and keep only the sourcing caveat as static prose.
